# macOS VPN Bypass Proxy

Локальный HTTP/HTTPS-прокси для macOS, предназначенный для выборочной маршрутизации браузерного трафика. Домены `.ru` и `.рф` направляются в обход VPN через физический Wi-Fi-интерфейс, остальные домены используют системный маршрут по умолчанию.

Проект является экспериментальным прототипом. Основной проверенный сценарий — macOS, Google Chrome, активный VPN-клиент, который маршрутизирует основной трафик через `utun`-интерфейс.

## Назначение

Проект позволяет оставить VPN включённым, но направлять часть браузерного трафика мимо него. Текущая политика маршрутизации:

```text
.ru / .рф     → Wi-Fi interface
остальное    → default route
```

При включённом VPN `default route` обычно проходит через VPN, а Wi-Fi-интерфейс используется только для явно выбранных доменов.

Текущая стабильная схема работает через отдельный экземпляр Google Chrome, запущенный с параметром:

```sh
--proxy-server="http://127.0.0.1:18080"
```

## Архитектура

```text
Google Chrome
    ↓
127.0.0.1:18080
    ↓
local Python proxy
    ↓
domain-based routing
    ↓
.ru/.рф → Wi-Fi interface
other   → default route
```

Прокси слушает только локальный адрес:

```python
LISTEN_HOST = "127.0.0.1"
LISTEN_PORT = 18080
```

Это ограничивает доступ к прокси текущей машиной. Внешние устройства в локальной сети не могут подключиться к `127.0.0.1`.

Для обхода VPN используется macOS-специфичная socket option `IP_BOUND_IF`, которая позволяет привязать исходящий IPv4-сокет к конкретному сетевому интерфейсу.

Wi-Fi-интерфейс определяется автоматически через:

```sh
networksetup -listallhardwareports
```

При необходимости его можно задать вручную:

```sh
BYPASS_IFACE=en1 ./start-proxy.command
```

Если автоматическое определение не удалось, используется fallback `en0`.

## Обработка трафика

HTTPS обрабатывается через метод `CONNECT`. Прокси извлекает домен назначения, выбирает маршрут, устанавливает TCP-соединение и далее передаёт данные между браузером и удалённым сервером.

Прокси не расшифровывает TLS-трафик, не подменяет сертификаты и не выполняет MITM-перехват. Для HTTPS он видит домен назначения, но не видит содержимое страниц.

Обычный HTTP-запрос обрабатывается как стандартный proxy request: абсолютный URL преобразуется в origin-form и пересылается на upstream-сервер.

## Почему Chrome, а не Safari

Safari использует системные proxy-настройки macOS и не поддерживает рабочий аналог Chromium-параметра `--proxy-server`.

В ходе тестирования было установлено:

* без VPN системный proxy macOS применяется, и Safari может работать через локальный proxy;
* при включении текущего VPN-клиента effective proxy-конфигурация macOS очищается;
* `scutil --proxy` при включённом VPN показывает только `FTPPassive : 1`;
* запуск Safari через терминал с proxy-аргументом не приводит к отправке трафика в локальный proxy.

Поэтому Safari в текущей реализации не поддерживается. Для него потребуется более низкоуровневое решение, например macOS Network Extension.

Chrome используется потому, что proxy можно задать на уровне конкретного процесса, независимо от системных proxy-настроек macOS.

## Требования

Проверенная среда:

```text
macOS
Python 3.11+
Google Chrome
zsh
Wi-Fi interface
VPN через utun-интерфейс
```

На Apple Silicon проект не требует отдельной компиляции и не использует бинарные зависимости. Достаточно доступной команды:

```sh
python3
```

Текущая реализация является macOS-only. 

## Установка

```sh
git clone <repo-url>
cd vpn-bypass-proxy
chmod +x start-proxy.command stop-proxy.command clean-data.command
```

Проверка зависимостей:

```sh
python3 --version
ls "/Applications/Google Chrome.app"
```

## Запуск

```sh
./start-proxy.command
```

Скрипт:

1. проверяет, занят ли порт `18080`;
2. запускает `main.py` в фоне, если proxy ещё не работает;
3. пишет логи в `proxy.log`;
4. открывает отдельный экземпляр Chrome с локальным proxy;
5. использует отдельный профиль `chrome-profile/`.

Фрагмент запуска proxy:

```sh
nohup python3 -u main.py > "$LOG_FILE" 2>&1 &
```

Ключ `-u` нужен, чтобы логи записывались сразу.

## Остановка

```sh
./stop-proxy.command
```

Проверить, что proxy остановлен:

```sh
lsof -nP -iTCP:18080 -sTCP:LISTEN
```

Если команда ничего не выводит, порт свободен.

Важно: если остановить proxy при открытом bypass-Chrome, этот экземпляр Chrome потеряет доступ к интернету. Это ожидаемо, потому что Chrome был запущен с обязательным proxy-server. Для обычного доступа используйте обычный Chrome или снова запустите proxy.

## Очистка данных

```sh
./clean-data.command
```

Удаляются runtime-данные:

```text
chrome-profile/
proxy.log
```

При следующем запуске профиль Chrome будет создан заново.

## Проверка работы

Проверить, что proxy слушает порт:

```sh
lsof -nP -iTCP:18080 -sTCP:LISTEN
```

Проверить `.ru`-домен:

```sh
curl -I -x http://127.0.0.1:18080 https://yandex.ru
```

Ожидаемый лог:

```text
[https host] yandex.ru
[route] BYPASS_VPN_VIA_WIFI
```

Проверить обычный домен:

```sh
curl -I -x http://127.0.0.1:18080 https://example.com
```

Ожидаемый лог:

```text
[https host] example.com
[route] DEFAULT_VPN
```

Просмотр логов:

```sh
tail -f proxy.log
```

## Ограничения

* Поддерживаются только домены `.ru` и `.рф`.
* Некоторые российские сервисы используют домены вне `.ru`, например `.net` или `.com`; они не обходят VPN.
* Safari не поддерживается в текущей схеме.
* PAC fallback не используется.
* Корректность обхода VPN зависит от политики конкретного VPN-клиента.
* Проект не является production-grade proxy.
* Код не реализует аутентификацию, DNS-over-HTTPS, собственный DNS resolver или SNI-анализ.
